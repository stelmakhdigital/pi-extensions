# Скорость: Core Web Vitals, вес, тормоза

Читать этот файл, когда экран медленно грузится или тормозит, когда нужно померить и не ухудшить, или перед сдачей тяжёлой страницы (картинки, список, сторонние скрипты). Порядок работы и отчёт по находкам — в `SKILL.md` рядом.

Порядок один: замер, правка, замер. Правки без пары замеров — гадание, а «ощущение отзывчивости» не проверяется. Числа в отчёте только из прогона, никогда не из предположения.

## Шаг 0 — что меряем и где

Лаборатория (chromium, скрипт ниже) годится для решений «правка улучшила или ухудшила». RUM (CrUX, `web-vitals` на проде) отвечает на вопрос «как у людей». Оба называть своими именами; лабораторное LCP не равен медианному RUM.

Что меряем: LCP (главный контент), CLS (сдвиги макета), INP (отклик на действие), TBT (блокировка основного потока), вес и число запросов.

```bash
# playwright ставится один раз в проверяемый проект
npm i -D playwright && npx playwright install chromium

# S — каталог этого скилла (pi сообщает путь к SKILL.md при загрузке), запускать из корня проверяемого проекта
S=<каталог скилла ui-review>
node "$S/scripts/perf.mjs" http://localhost:3000 --click "button.menu" --wait 1500
node "$S/scripts/perf.mjs" http://localhost:3000 --budget lcp=2500,cls=0.1,inp=200 --strict
node "$S/scripts/perf.mjs" http://localhost:3000 --slow --json    # сеть как 4G
```

`--click` обязателен, когда правим отзывчивость: без действий после загрузки INP не измеряется и скрипт об этом напишет. Против `file://` ресурсная статистика неполная — мерить против dev-сервера или `preview`.

## Шаг 1 — где лежит вес, а не где кажется

Читать вывод по порядку:

1. `Вес по типам` и `Самые долгие запросы` — что занимает место и время. Обычно первое по отдаче: картинки, шрифты, JS.
2. `Картинки отданы крупнее, чем показаны` — самый частый источник лишних сотен КБ; `2x` при показе 300 px — это в 4 раза лишний вес.
3. `Сдвиги макета (кто двигал)` — у CLS всегда есть конкретный mover: картинка без размеров, вставленный баннер, шрифт, подменяющий метриками.
4. `TBT` и число длинных задач — если больше 200 мс, тормозит JS, а не сеть: смотреть, что парсится и рендерится в основном потоке.
5. LCP: из чего собран элемент (картинка, заголовок, блок после fetch) — чинится по источнику, а не «оптимизируем всё».

## Шаг 2 — порядок правок

Идти сверху вниз, по одной правке, с замером после каждой:

1. Критический путь: LCP-элемент не должен ждать JS, fetch-а или стороннего скрипта; нужное — inline/preload, не нужное — `defer`.
2. Картинки: правильный формат (`avif`/`webp` с fallback), `width`/`height` или `aspect-ratio`, `srcset`/`sizes`, `loading="lazy"` вне первого экрана, `fetchpriority="high"` на LCP-картинке.
3. Шрифты: `font-display: swap` (или `optional`), `preload` на используемые начертания, `size-adjust`/`ascent-override` на fallback, иначе подмена даёт CLS; subsets по письменности.
4. JS: код по месту использования, динамические импорты на тяжёлые виджеты, сторонние скрипты (аналитика, чаты, видео) — после интерактивности или в worker; полифилы по условиям.
5. Список и таблица: виртуализация или страница; 5 000 DOM-узлов в таблице — это и CLS, и INP, и память.
6. Кеш и CDN: `immutable` на хешируемых ресурсах, предзагрузка следующего экрана (`prefetch`) там, где переход вероятен.

`prefetch`/`preconnect` всего подряд — не оптимизация, а перенос бюджета на ненужные запросы.

## Шаг 3 — keep or revert

После каждой правки — повторный замер теми же флагами и тем же профилем сети:

- Улучшило цель и не ухудшило другую метрику — оставляем, в отчёте обе цифры.
- Улучшило одну метрику за счёт другой — решение называется явно (что и кем пожертвовано), а не «немного хуже, но чище».
- Не улучшило или улучшило в пределах шума (единицы мс при лабораторном шуме в десятки мс) — откатываем правку, а не оставляем «на всякий случай».

## Шаг 4 — гард от регресса

Чтобы правка не сдохла через месяц:

- В CI — `perf.mjs <preview-url> --budget ... --strict` против собранного превью на каждый push (или на ветки с правками фронта). Бюджет ставится от текущих чисел с запасом 10-15%, а не с потолка.
- Числа до/после коммита — в сообщении коммита или в PR.
- Бюджет на вес бандла — там, где он собирается (`size-limit`, `bundlesize`), а не только по времени загрузки.
- Лабораторные прогоны в CI шумные: порог закладывать с запасом и падать только на превышении бюджета, а не на «стало на 30 мс дольше».
