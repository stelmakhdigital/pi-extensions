# edit-check (расширение pi)

Проверка типов/линта в конце прогона, чтобы модель узнала, что сломала код.

`edit-fresh` ловит «правку по устаревшему read», но если `oldText` совпал, а
правка сломала типы — инструмент отдаёт успех, и модель рапортует «готово» с
красным проектом. LSP-обвязка (pi-lens) закрывает это на каждом редактировании,
но это отдельный большой слой с language server на язык. Здесь дешёвая версия:
одна проверка на завершение гонки.

## Как работает

1. `tool_result(edit|write)` без ошибки -> помечаем «грязно».
2. `agent_settled` (гонка дошла до конца) и грязно -> запускаем команду проекта
   и ждём её (в футере `check…`).
3. Ненулевой exit -> первые N строк вывода уходят модели сообщением с
   `triggerTurn`: прогон не завершается со сломанным кодом молча, у модели есть
   шанс починить.
4. После 3 таких раундов цикл обрывается: остаётся бейдж `⚠ проверки не
   проходят` и одно предупреждение пользователю. Модель, которая трижды не
   справилась, четвёртый раз не герой.

Успешная проверка сбрасывает счётчик и снимает бейдж.

## Команда проверки

Берётся первое совпадение:

1. `.edit-check.json` в CWD: `{ "cmd": "npm run check", "max": 10, "timeoutMs": 180000 }`;
2. script проекта: `typecheck` / `type-check` / `check-types` / `tsc`;
3. `npx --no-install tsc --noEmit`, если в самом CWD есть `tsconfig.json` и рядом
   (вверх по дереву) есть `node_modules/.bin/tsc`. tsconfig родителя без
   запускаемого tsc проверки не создаёт: в пакете монорепа `npx` падал с кодом 1, и
   модель получала три раунда «проверка упала» ни за что.

Команды нет -> расширение молчит без единого сообщения (в JS-скриптах шуметь
незачем). Парсинг вывода простой: строки со словом `error` (формат tsc
`a.ts(3,7): error TS2345: ...`, eslint-таблицы), иначе — весь вывод; кап `max`
строк, таймаут по умолчанию 3 минуты.

## Управление

| Команда | Действие |
|---|---|
| `/edit-check` | запустить проверку сейчас и показать результат в уведомлении |
| `/edit-check off` / `on` | выключить/включить (персистентно, `guard-state.json`) |
| бейдж | `check…` идёт проверка, `✗ 2/3` сколько раундов отдано, `⚠ проверки не проходят` — всё, дальше решает человек |

В yolo работает как обычно: сообщение со списком ошибок — ровно то, чего в
автономном прогоне не хватало.

## Границы

- Проверка одна на прогон: между правками внутри хода модель ошибок не видит
  (за это отвечают LSP-расширения), и длинные прогоны с медленным `tsc`
  получают +секунды к финалу.
- Команда запускается через `sh -c` с правами процесса pi — как и любой `bash`
  инструмент. `.edit-check.json` чужого репозитория задаёт, что выполнится:
  в недоверенном проекте доверяй проекту, а не этому файлу.
- `lint` в defaults сознательно нет: линтер с сотней warn превращает каждый
  финал прогона в простыню. Нужен — пропиши `cmd` в `.edit-check.json`.

## Тесты

дочерний процесс: правка + падающая проверка (текст ошибки дошёл, `triggerTurn`

дерево, `MAX_REPORTS` и предупреждение, ручной `/edit-check`, `off`/`on`,
тишина в проекте без команды.
