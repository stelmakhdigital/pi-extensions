# yolo (расширение pi)

Один выключатель автономности: агент получает максимальные права, ни стартовый
вопрос, ни guard его не останавливают. Нужен там, где в TUI никто не ответит —
Orca-автоматизации, CI, конвейеры, `pi -p`. Включается и выключается и на старте,
и посреди сессии.

## Включение

```bash
pi --yolo "задача"            # или
PI_YOLO=1 pi "задача"         # переменная наследуется дочерними pi
pi --yolo --mode rpc          # работает в любом режиме
```

`PI_YOLO=1` достаточно для Orca: задай переменную в окружении автоматизации и
не трогай команду запуска. Флаг и переменная дают один и тот же режим; флаг
виден в `pi --help`, переменная — в `env`.

Третий способ — команда `/yolo` в уже идущей сессии: переключает режим в обе
стороны, ничего не перезапуская.

## Что выключается

| Источник вопроса/блокировки | В yolo |
|---|---|
| «Trust project folder?» (pi, `project_trust`) | авто-доверие на этот процесс, в `trust.json` ничего не пишется |
| «Доверяешь ли ты проекту?» + изоляция bash (`sandbox`) | ни своего промпта, ни обёртки bwrap/sandbox-exec |
| «Restart pi inside tmux?» (`subagents`) | вопрос не задаётся, в tmux не переезжаем |
| запросы и блокировки `bash-guard` | нет, включая «пол» катастрофических операций |
| блокировки путей `dir-guard` | нет |
| `edit-fresh` (edit без свежего read) | нет |
| `text-guard` (стиль текста) | нет |
| confirm-гейт браузера (`agents-web-search`) | действия разрешаются автоматически |

Не трогается: `ask_user_question` — вопрос, который модель задала сама,
остаётся вопросом (в headless он и так не имеет UI).

## Что умеет `/yolo`

Снимает и возвращает блокировки guard'ов и бейджа (`YOLO`, `TG …`, `sandbox: …`
обновляются на глазах). Переключение держит `PI_YOLO` в синхроне (`1`/`0`),
поэтому дочерние процессы — rpc-агенты конвейера, `pi`, запущенный из bash —
наследуют актуальное состояние.

Команда не всесильна:

- Вопросы старта — «Trust project folder?» и tmux-handoff — она не отменяет. Они
  случаются раньше, чем в сессии можно ввести команду; для них нужен `--yolo`
  или `PI_YOLO=1` при запуске.
- После `/reload` factory перечитываются, и состояние берётся из env/argv:
  включение переживёт перезагрузку (env синхронизирован), выключение — нет, если
  pi запущен с `--yolo` (флаг остался в argv). Тогда `pi -c` без флага.
- tmux-панели субагентов берут окружение tmux-сервера, а не родительского pi:
  чтобы субагенты тоже были в режиме, запускай tmux с `PI_YOLO=1`. В дефолтной
  конфигурации субагенты и так идут с `--no-extensions` — guard'ов в них нет.

## Как это устроено

`extensions/yolo-mode.ts` — общий хелпер `isYolo()`: переключатель `/yolo`,
иначе `PI_YOLO`, иначе `--yolo` в argv до разделителя `--` («--yolo» внутри
текста промпта режим не включает). Guard'ы спрашивают `isYolo()` в момент
блокировки, а не в factory: регистрация обработчиков не зависит от режима, зато
работает переключение в обе стороны. Порядок загрузки расширений не влияет —
проверяются окружение и argv, а не `pi.getFlag`.

Расширение стоит первым в `pi.extensions` — у `project_trust` решение берёт на
себя первый вернувший yes/no обработчик. Без режима yolo отвечает `undecided` и
не мешает `sandbox` задать свой уровень.

## Границы

yolo снимает защиты, которые ты поставил сам, и не трогает изоляцию уровня ОС:
bwrap/Docker/Gondolin по-прежнему решают, что реально доступно процессу. Для
неизвестного кода предпочтителен `--sandbox-level dev` (изоляция без вопросов),
а не yolo.

Состояние guard'ов (`~/.pi/agent/guard-state.json`) читается и пишется как
обычно — в режиме оно просто ни на что не влияет: `isYolo()` проверяется раньше
переключателей `BG OFF`/`DR OFF`/режима text-guard. Бейдж `⚠ YOLO` виден, когда
режим включён.
